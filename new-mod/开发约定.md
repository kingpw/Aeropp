# Aeropp 单模组开发约定

版本：0.2

本约定适用于 Aeropp 项目中的一个 NeoForge 模组。目标是：能从干净检出状态构建、能在整合包外独立测试、能让世界生成和玩法规则持续演进。

## 1. 固定基线

- Minecraft `1.21.1`
- NeoForge `21.1.248`
- Java `21`（64 位）
- Gradle Wrapper + NeoForge ModDev 插件
- 一个模组项目只使用一个 `mod_id` 和一个资源命名空间。
- 源码、资源、配置和数据文件必须足以复现构建；不依赖本机测试 JAR。
- 测试版模组 JAR 文件名必须使用 `test-` 前缀，例如 `test-aeropp_mobtest-0.1.0.jar`；正式发布模组不得使用该前缀。

## 2. 目录结构

```text
<mod-project>/
├─ build.gradle / settings.gradle / gradle.properties
├─ gradlew / gradlew.bat / gradle/wrapper/
├─ README.md / CHANGELOG.md / LICENSE
├─ src/main/java/<base-package>/
│  ├─ <ModName>.java       # 唯一入口
│  ├─ bootstrap/           # 注册和生命周期接线
│  ├─ content/             # 方块、物品、实体、菜单
│  ├─ gameplay/            # AI、规则、状态机和服务接口
│  ├─ worldgen/            # 世界生成运行时服务
│  ├─ event/               # NeoForge 事件适配
│  ├─ network/             # 客户端同步
│  └─ util/                # 无状态工具
├─ src/main/resources/
│  ├─ META-INF/neoforge.mods.toml
│  ├─ pack.mcmeta
│  ├─ assets/<mod_id>/
│  └─ data/<mod_id>/
└─ docs/                   # 设计、兼容性和测试记录
```

没有实际内容的包可以暂不创建。`build/`、`.gradle/`、`run/`、日志和存档必须被忽略。

## 3. 代码职责

- 入口类只负责初始化和接线，不写业务逻辑。
- 注册集中在 `bootstrap` 或 `content`；注册名使用小写蛇形，例如 `sky_fortress`。
- `event` 只做事件筛选和调用，不在 Tick 回调中堆叠规则。
- `gameplay` 保存可测试的规则和状态；不得引用客户端专属类。
- 客户端渲染、按键和屏幕只能由客户端初始化代码引用。
- 与其他模组交互时使用公开 API、事件或标签，不依赖私有实现。

## 4. 接口约定

跨包或未来跨模组的能力先定义接口，再提供实现。例如：

```java
public interface StructureScenarioService {
    ScenarioId create(ScenarioRequest request);
    ScenarioState state(ScenarioId id);
    boolean reset(ScenarioId id, ResetReason reason);
}
```

- 参数使用不可变值对象。
- 文档注明调用侧别、权限、失败条件和幂等性。
- 不用 `null` 表示业务分支；使用明确的状态或结果类型。
- 服务端保持权威，网络层只同步客户端需要显示的数据。

## 5. 数据与世界生成

- 静态结构放在 `data/<mod_id>/worldgen/structure`。
- 生成频率和分布放在 `worldgen/structure_set`，范围用 biome tag 控制。
- 设计记录必须写明生成步骤、`spacing`、`separation`、`salt` 和限制条件。
- 能用 JSON、标签、配方、战利品表表达的内容，不写成 Java 硬编码。
- 事件副本、可重置建筑和任务目标必须另建实例 ID、状态和持久化服务，不能只依赖原版结构生成。
- 不在每个区块 Tick 中直接放置结构；动态建筑使用显式场景服务，并保证重载幂等。

## 6. 敌人与任务

- 实现前先写职责、目标、攻击窗口、生成上限和玩家反制方式。
- 批量单位、突击单位和重型单位使用不同生成入口。
- 方块破坏必须有白名单、冷却、范围、来源和恢复策略。
- FTB Quests 负责展示、条件和奖励；事件状态由模组服务维护，以稳定 ID 连接。

## 7. 配置与兼容性

- 平衡参数优先放服务端配置或数据文件，并注明默认值、范围和单位。
- 配置改名必须提供迁移说明或兼容读取。
- `neoforge.mods.toml` 写明必需依赖、版本范围和运行侧别。
- Minecraft、NeoForge 或关键前置升级时，记录启动、单人、多人和存档迁移结果。

## 8. 验证与提交

最低验证：

1. `gradlew build` 成功，JAR 包含元数据和预期资源。
2. 客户端能创建新世界，服务端能启动、停止和重启。
3. 新世界和已有世界重载各测试一次。
4. 使用 `/locate structure <mod_id>:<structure>` 或专用命令验证世界生成。
5. 按目标人数测试实体数量、区块加载和服务器性能。

提交：

- 分支：`feature/<topic>`、`fix/<topic>`、`docs/<topic>`。
- 提交信息：`范围：动作`，例如 `worldgen：添加主世界末地城结构集`。
- PR 记录改动、版本兼容性、测试环境、已知限制和迁移说明。
- 测试产物进入整合包 `mods/` 时保留 `test-` 前缀，并在转为正式版本前更换文件名和发布记录。
