# Aeropp 模组制作经验总结

本文记录本次从整合包现状分析到建筑测试模组构建的可复用经验。

## 1. 先分清整合包和模组工程

原有 Aeropp 是 packwiz 整合包源文件，包含模组元数据和配置，但不包含可维护的自研 Java 源码。`testmod-1.0.0.jar` 虽然已被索引，却不能作为长期开发边界。

结论：自研内容必须建立独立 Gradle 工程；整合包只消费构建产物和配置。源码、资源、版本和构建方式都必须提交，避免“本机有 JAR、其他人无法复现”。

## 2. 版本和构建环境必须先锁定

NeoForge `21.1.248` 要求 Java 21。系统默认 Java 17 时，Gradle 会在工具链阶段失败，即使代码本身没有错误。

结论：

- 在 `gradle.properties` 固定 Minecraft、NeoForge 和模组版本。
- 提交 Gradle Wrapper，统一 Gradle 版本。
- README 明确 Java 21 的要求和运行任务。
- 构建失败时先区分环境错误、依赖下载错误和源码错误。

本次使用 Minecraft 启动器自带的 Java 21 完成构建，最终 `build` 成功。

## 3. 世界生成优先采用数据驱动

建筑测试模组没有在区块事件中手动放置方块，而是拆成：

1. `worldgen/structure`：定义结构类型、起始池、生物群系和生成步骤。
2. `worldgen/structure_set`：定义随机分布、间距和盐值。
3. biome tag：控制允许生成的范围。

这种方式更接近原版和 NeoForge 的世界生成模型，便于之后替换模板、调整范围或由数据包覆盖。

本次复用了原版 `minecraft:end_city/towers` 起始池，因此末地船仍遵循末地城内部的原版随机分支，并不是独立必然出现的结构。

## 4. “与村庄相同”需要精确定义

村庄的“生成概率与位置”不是一个单独开关，而是结构集的随机扩散参数。本次实验使用与村庄相同的：

- `spacing = 34`
- `separation = 26`
- `salt = 10387312`

这意味着候选网格分布相同，但最终数量仍会受到生物群系、地形合法性和结构冲突检查影响，不能承诺所有世界中数量完全一致。

## 5. 静态结构和事件建筑要分开

静态世界生成适合探索型建筑；战斗靶标、可破坏建筑和副本则需要建筑实例 ID、团队归属、当前状态、重置规则和持久化。

结论：先用结构集验证“能否生成”，再实现场景服务验证“能否重复使用”。不要把任务状态、奖励和修复逻辑直接塞进结构 JSON 或 Tick 回调。

## 6. 验证不能只停留在编译

本次确认了三层验证：

- 文件层：JSON、模组元数据和资源路径可解析。
- 构建层：JAR 包含 Java 类、`neoforge.mods.toml` 和全部世界生成资源。
- 游戏层：使用 `/locate structure`、新世界、重载世界和多人场景验证实际生成与性能。

其中游戏层仍需在 PCL2 或独立测试实例中完成，尤其要确认末地城在主世界的地形适配、末地船出现率和结构间距。

## 7. 推荐的后续工作流

1. 先写玩法目标和可测指标。
2. 建立可复现的单模组 Gradle 工程。
3. 先用数据文件做最小垂直切片。
4. 编译、检查 JAR，再进入独立游戏实例。
5. 通过后再加入实体事件、任务桥接、重置和整合包索引。
6. 最后才扩大自然生成数量或增加高成本实体。

这套顺序可以把“设计问题”“工程环境问题”和“游戏平衡问题”分开定位，减少反复修改整合包的成本。
