# Aeropp

> 以机械动力工业化生产物理载具，在柴油朋克世界中经营航空工业、完成城镇订单，并将科技产能投入运输、探索与战争。

Aeropp 是一个正在开发中的 Minecraft Java 版科技冒险整合包。项目以 **Create** 与 **Create: Aeronautics** 为核心，尝试把机械动力的生产目标从普通物品进一步扩展为可以实际驾驶、运输和战斗的物理载具。

玩家将从基础零件与简单结构开始，逐步建立航空工业产线，按照标准蓝图制造飞艇、飞机和其他物理船体；通过城镇订单、运输合同与地区任务获取工票、技术许可和新蓝图，最终发展出能够支持自由载具设计、自动航空物流及大规模战争消耗的工业体系。

## 核心玩法

Aeropp 的核心循环为：

```text
接受城镇订单
    ↓
获取标准蓝图与材料清单
    ↓
建立机械动力零件产线
    ↓
组装或打印航空学物理船体
    ↓
试飞、运输或交付成品载具
    ↓
获得工票、工业声望与技术许可
    ↓
解锁新蓝图、加工技术、地区和合同
    ↓
用更强的科技产能应对物流与战争需求
```

项目不以无限堆叠科技模组为目标。机械动力负责主要生产过程，航空学物理载具负责承载生产成果，运输、探索和战争则构成科技产能的使用与消耗端。

### 标准化生产与自由设计

载具制造计划分为两个阶段：

- **前中期：标准蓝图与固定订单。** 玩家按照系统提供的标准蓝图制造载具，系统可以可靠地检查解锁状态、材料消耗与交付结果。
- **后期：自由设计与试飞认证。** 玩家可以自行设计载具，通过航程、载荷、飞行高度、稳定性或规定路线等试飞项目完成型号认证。认证成功的设计可保存为团队蓝图，后续同型号载具不再重复试飞。

雕像、傀儡、炮塔等广义实体结构不会取代成品载具，而是作为前期教学、辅助订单，以及玩家暂时无法制造完整载具时的替代进度路线。

## 发展阶段

### T0：航空学徒

- 学习机械动力和航空学的基本操作。
- 制造螺旋桨、轴承、传动组件和基础结构件。
- 完成模型、雕像、固定炮塔等入门订单。
- 手工搭建第一台简易载具，避免开局就被大型产线阻挡。

### T1：标准化制造

- 获得第一批标准载具蓝图。
- 建立基础零件自动化和装配设施。
- 制造小型货运飞艇或同等级飞行器。
- 完成第一次物理载具交付和短途运输任务。

### T2：航空工业

- 订单开始要求批量零件和重复型号载具。
- 解锁燃料、维修、弹药和高级结构件生产。
- 承接运输、侦察和护送任务。
- 建设机场、码头与团队工业基地。

### T3：航空战争

- 敌对强度按照任务进度和地区提升，而不是单纯按照世界时间增长。
- 引入敌对飞行器、地面目标、防空威胁和地区敌袭。
- 标准军用载具、燃料、弹药及维修件形成持续消耗。
- 逐步解锁自动航线与航空物流网络。

### T4：自由设计

- 开放自由载具设计和性能认证。
- 将通过认证的设计保存为个人或团队蓝图。
- 高性能设计用于解锁特殊合同、困难地区和终局挑战。
- 自由设计提供更高上限，但不会成为无限刷取奖励的漏洞。

## 经济与进度

目前计划使用两层奖励体系，具体数值仍在设计中。

### 工票

通过可重复订单获得，用于：

- 购买基础资源和生活物资；
- 支付蓝图打印、维修和载具保险费用；
- 购买燃料、消耗品及部分工业服务；
- 扩建工业用地、机场和物流设施；
- 获取不影响主线平衡的装饰与便利物品。

### 航空工业声望与技术许可

主要通过首次完成、章节任务和地区目标获得，用于：

- 解锁标准载具蓝图；
- 解锁高级加工配方；
- 解锁武器、雷达、控制与自动物流技术；
- 开放新地区、机场和合同类型；
- 获取自由设计与试飞认证资格。

第一台基础飞行器原则上可以手工制造；随着订单规模扩大，自动化工厂将从“可选优化”逐渐变成完成订单、补充战争消耗和扩展航空网络的必要基础设施。

## 世界观与风格

项目暂定采用 **中世纪外观的柴油朋克 / 发条航空文明**：

- 城镇、工坊与公共建筑保留中世纪聚落轮廓；
- 齿轮、锅炉、帆布、木材、铆钉和金属骨架构成工业视觉语言；
- 航空工业正在改变传统城镇之间的贸易、战争和社会结构；
- 新建筑必须服务于任务、生产、运输、探索或战斗，不单纯为了增加结构数量；
- 世界地形应提供足够连续的平原、海域和山地，保证长距离飞行体验，避免过度破碎的群系分布。

最终建筑风格、阵营关系和主线剧情仍需随着世界观设计继续完善。

## 单人与多人

Aeropp 的主线必须能够由单人完成，同时支持多人团队分工。

- 使用 FTB Teams 与 FTB Quests 统一同一团队的主要任务进度。
- 难度以任务章节和区域为主要依据，避免缺席玩家因世界时间增长而完全掉队。
- 关键蓝图、许可证和Boss进度应以团队为单位处理。
- 载具、机场和自动物流需要明确个人、团队及盟友权限。
- 多人会提高订单效率，但不应成为进入主线内容的硬性要求。

## 最小可玩版本

首个 Demo 计划控制在约3至5小时，目标是验证完整玩法闭环，而不是提供最终内容量。

计划包含：

- 1座中世纪柴油朋克城镇；
- 1个订单大厅或订单系统；
- 1条基础机械动力生产线；
- 模型、炮塔或其他简单结构订单；
- 1张小型货运载具标准蓝图；
- 零件生产、成品交付和实体运输三类任务；
- 1次地区敌袭或飞行战斗事件；
- 1个支持单人和FTB团队共享的任务章节。

Demo暂不包含：

- 通用自由载具自动验收；
- 跨维度载具运输；
- 大规模多维度内容；
- 完整自动航空物流网络；
- 大量自研敌人与复杂地牢；
- 大规模剧情和终局内容。

## 技术验证重点

物理载具、机械动力设备和多人服务器的组合存在较高的性能及存档风险。开发过程中需要持续测试：

- 不同体积物理船体的装配、拆卸与碰撞；
- 区块卸载和重新加载后的载具完整性；
- 服务器正常重启和异常退出后的恢复；
- 蓝图保存、打印、删除和重复打印；
- 容器、机械方块及子物理结构是否产生复制漏洞；
- 单人、双人和四人环境中的TPS与客户端帧率；
- 多台活动载具及敌对实体同时存在时的性能；
- FTB团队成员加入、退出和离线时的所有权处理；
- 自动备份、问题载具回收与存档回滚。

在核心技术验证通过前，不会大量加入世界生成、光影、维度或高负载内容。

## 开发路线

- [ ] **阶段0：基础环境**——确定核心模组、版本锁定、客户端与专用服务端工作流。
- [ ] **阶段1：物理船体验证**——测试装配、飞行、蓝图、重启、多人和性能。
- [ ] **阶段2：垂直切片**——实现零件生产、标准载具制造、交付和奖励闭环。
- [ ] **阶段3：任务与经济**——建立团队进度、工票、技术许可及基础教程。
- [ ] **阶段4：战争消耗端**——加入地区难度、敌袭、维修、燃料和弹药消耗。
- [ ] **阶段5：世界内容**——制作城镇、机场、地区目标及世界观内容。
- [ ] **阶段6：封闭测试**——进行单人和四人完整流程测试、平衡与性能优化。
- [ ] **阶段7：Demo发布**——提供经过验证的客户端、服务端和安装文档。

自研功能按照核心程度排序：

1. 标准载具订单、蓝图解锁、成品交付与团队奖励的桥接系统；
2. 自由载具试飞与型号认证系统；
3. 特殊敌人、跨维度载具和差异化物理环境。

在编写新Mod前，优先验证现有模组、配置、数据包和KubeJS能否完成需求。

## 本地开发

本仓库使用 [packwiz](https://packwiz.infra.link/) 管理模组版本和文件索引，当前使用 PCL2 创建、导入并启动本地测试实例。

首次获取仓库：

```powershell
git clone https://github.com/kingpw/Aeropp.git
cd Aeropp
```

使用packwiz添加模组：

```powershell
.\packwiz.exe modrinth add <模组链接或项目ID>
# 或
.\packwiz.exe curseforge add <模组链接或项目ID>
.\packwiz.exe refresh
```

导出临时测试包：

```powershell
New-Item -ItemType Directory -Path build -Force | Out-Null
.\packwiz.exe modrinth export -o build/Aeropp-0.1.0.mrpack
```

在PCL2中导入生成的 `.mrpack`，并为该实例指定64位Java 21。测试通过后只提交配置、脚本、资源和packwiz元数据，不提交下载的模组JAR、日志、缓存或测试存档。

## 协作约定

- `main` 只保留已知可启动、可测试的版本。
- 功能开发使用 `feature/*` 分支，问题修复使用 `fix/*` 分支。
- 每次只加入少量模组，并记录加入目的、依赖、兼容性和测试结果。
- Minecraft、NeoForge、Create、Create: Aeronautics或Sable升级必须单独提交PR。
- 配置和脚本修改必须说明影响的玩法与验证方式。
- 任何成员都不应直接提交模组JAR、日志、崩溃转储或包含玩家信息的存档。
- 模组和资源必须来自可信来源，并遵守各项目的分发与修改许可。

## AI辅助开发

团队成员均处于整合包开发学习阶段，项目会使用AI辅助：

- 整理需求与设计文档；
- 筛选候选模组及分析依赖；
- 编写小规模KubeJS脚本和配置修改；
- 分析崩溃日志与性能报告；
- 生成测试清单、任务文本和更新日志；
- 为自研Mod生成脚手架和局部实现建议。

所有AI生成内容都必须经过人工检查和实际游戏验证。AI不能替代玩法体验、版本兼容性测试、代码审查和发布责任。
